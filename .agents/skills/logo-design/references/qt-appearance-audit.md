# Qt appearance audit and acceptance

Use for shared Qt Widgets changes, read-only theme audits, settings regressions and framework evaluation. For DB Tree only, use the local tree workflow and keep the global theme outside the edit scope. [ACloudViewer resource cases](<acloudviewer-resource-cases.md#db-tree-local-migration-and-acceptance>).

## Trace the production lifecycle

1. Run `pwd`, `git status --short` and collect read-only source hashes before probing. Include startup, application owner, menus, dialog, settings, QSS/QRC, backend/build code and affected shared helpers. Hash approved DB Tree assets and any approved local styling, ParaView functional icons, plugin artwork and the complete excluded AnyLabeling tree as separate scopes. Record the audited file list and SHA-256. Work in a writable review directory outside the source tree when possible. For read-only work, use scratch build and output locations and leave production files, index, dependency installation and real user settings alone.
2. From the repository root, find actual callers and verify the current files and lines. The historical paths and symbols in this search are starting points.
   ```bash
   rg -n 'ecvSettingManager::Init|setAppStyle|applyAppearance|changeStyle|ChangeStyle|CurrentTheme|setStyleSheet|setPalette|applyTheme' app libs/CVAppCommon libs/CVPluginAPI
   rg -n 'sample-data|makeSampleDataBtn|QComboBox|setStyleSheet|setPalette' plugins/core/Standard/qOpenPCDet libs/CVPluginAPI
   ```
   Follow `app/main.cpp` from settings initialization to first window/show, `ecvApplicationBase` to style, theme, resource, palette and persistence, `MainWindow` and `ecvUIManager` to menu selection, and `ecvDisplayOptionsDlg` to preview, Apply, reject and acceptance. Trace `ecvComponentStyle` if it exists and follow the active replacement backend if present. Inventory actual consumers and report source lines, order, input settings/legacy keys, side effects, and whether each path is covered by a probe. Include per-widget QSS/Palette, shared helpers and plugin dialogs. In the historical conflict, style selection installed Native and then unconditionally applied a proxy and QSS. A separate green sample-data button came from a shared local helper. Verify both on current source. Trace window decorations before attributing them to Qt or the window manager.
3. Put state and persistence in the existing application appearance owner. Preserve base themes, defaults and approved local exceptions. Native includes platform/System and exposed factory styles such as Fusion/Windows. It has no Custom proxy/backend or application QSS overlay. Explicit Custom uses one active backend or one overlay on its intended base. Confirm repeated application leaves just one layer, with no duplicate QSS, registration or residual hooks. Treat old keys as migration inputs only and verify canonical state takes precedence. Validate incoming theme resources before mutation. Theme selection in Native must not change active appearance or persisted state. Restore inherited application palette/font and practice particular care with disabled colours on already-open Qt 5 widgets. Preserve explicit local palette roles, and avoid recolouring approved multicolour art.
4. In read-only work, exercise at least one risky state via a minimal configured-Qt probe and retain raw messages. Sibling widgets opened before a Custom-to-Native transition can expose inherited disabled-role residue while testing that a widget with an explicit local role survives. If the production code cannot be linked, label the reproduction as a reduced probe and identify missing real-owner coverage. Rehash audited inputs before conclusions. If a file changed concurrently, preserve the change, reread the current source, retake the relevant baseline, rebuild or rerun affected probes and record old/new hashes and invalidated results. Report whether the audit itself edited production code. Propose phases in this order when requested: settings correctness and warnings, ownership consolidation, consumer coverage with shared geometry/colour/state definitions, then broader production acceptance.

## Configured build and runners

1. Select the intended build by inspecting its `CMakeCache.txt`, `compile_commands.json` or target metadata. Record `USE_QT6`, `Qt5_DIR`/`Qt6_DIR`, build type, platform, compiler and `qVersion()` from the probe. Use that build's Qt `rcc`, `uic`, includes, definitions, linked libraries, generated UI and resources, and matching runtime library/QPA paths. Check which definitions determine types and ABI if an external probe fails to compile. A missing complete type may require its header, such as `QPalette`, `QFont` or `QScreen`. If a literal edit fails, reread the current anchor before retrying.
2. From the repository root, set `build` to the configured build directory and `out` to a fresh writable run directory. Inspect the current runner sources for coverage and required environment before invoking them. The paths here are repository entry points. TODO resolve equivalent entry points or missing assertions on branches without these runners. Build the real targets on an authorised build; for a read-only audit use existing matching binaries or build in scratch and preserve production sources.
   ```bash
   git diff --check
   cmake --build "$build" --target CVAppCommon -j "${BUILD_JOBS:-4}"
   python3 scripts/icon_hd/verify_appearance_modes.py --build "$build" --out "$out/owner"
   python3 scripts/icon_hd/verify_qt_components.py --build "$build" --out "$out/components"
   cmake --build "$build" --target ACloudViewer -j "${BUILD_JOBS:-4}"
   ```
   The full component run has no `--theme` filter. A supported `--theme paraview` filter is useful during diagnosis only. Rebuild actual affected plugin targets if a shared helper changed. For the OpenPCDet example, confirm tests exist and use the configured Qt environment before running `ctest --test-dir "$build" -R 'test_qopenpcdet_(dialog|helpers)$' --output-on-failure`. Capture commands, logs and exit codes. Check expected test and scenario counts, including failures, skips and absent tests. Gather relevant background job results before publishing.

## Real settings and component matrix

1. **Settings probe.** Link the actual configured `CVAppCommon` and instantiate the real Display Options dialog. With isolated paths for both Qt settings and the application setting manager, run fresh default/Native and saved Custom cases at 1× and 2×. Through real combo, buttons and window events verify preview changes runtime without writing settings. Cancel, Esc and window close restore the full last committed state, including mode and preset. Exercise Apply followed by another preview and each rejection path so the rollback baseline is the newly applied state. OK commits. Check that Native theme selection and invalid preset selection leave persistence intact. Use a separate process against the same isolated store after the writer exits and assert startup restores the saved Custom preset through the production restore path. Include old-key-only fixtures, canonical precedence and repeated startup/apply cases.
2. **Backend and palette assertions.** Inspect `QApplication`'s current concrete style/backend and resulting state. For a Qlementine checkout, assert the real Qlementine instance in Custom. For a proxy checkout, assert a single live proxy on the preserved base and one QSS application as appropriate. Legacy markers alone are insufficient after a backend replacement. On return to Native assert the expected actual Native style, empty app QSS and inherited disabled-role recovery in already-open controls against the Native baseline. Assert an explicit per-widget local palette survives. Exercise new widgets too. For standard icons request `standardIcon()` from the current application style and examine real normal/disabled renders. Direct SVG/QRC samples serve as separate resource evidence.
3. **Components and density.** Enumerate expected rows from the actual app preset and mode list, including Native and QDarkStyle light/dark where offered. For Custom replacement run the whole preset matrix at 1×/1.5×/2×. For an incremental comparison, capture true before/after per theme at 1× plus the requested representative 2× cases. Use the matching baseline build and record which modes are available in each version. Exercise real widgets with a dense layout and event assertions for menu, editable and regular combo popup, spin stepping, and checkbox unchecked/checked/partial. Cover hover, focus, selection, disabled and keyboard interaction. Check geometry and fit, especially the combo frame, text, arrow hit area, focus ring, popup list, spacing and transitions. Include dock tabs and floating docks, vertical toolbars and overflow, tab overflow, calendar navigation and editors where applicable. For each platform note which cases actually ran.
4. **DPR and lifecycle.** Capture actual reported widget and pixmap DPR, logical dimensions and physical pixels. Compare physical dimensions to logical size × actual DPR with at most documented integer rounding. Show popups in valid available screen geometry and settle events before grabbing. On dimension failure record geometry, both DPRs and pixel sizes. Confirm the popup is on-screen before deciding whether the failure is in the harness or app. Keep size assertions. Exercise Custom → Native while a menu/popup or animation is active, including a menu action switching modes synchronously where supported. Settle events to expose stale callbacks. Verify repeated switches recover appearance and existing application-provided item delegates retain identity. Inspect animation disable/enable behaviour where implemented.

## Warning gates and delivery

1. Install Qt message capture before theme registration/application. Preserve full messages and stderr across registration, apply, show, interactions, restoration and restart. Check intended resource packs explicitly. Categorise and count stylesheet parse, missing or invalid image/resource, invalid regex, unknown/unsupported QSS property, platform plugin and other messages per run. Parse, resource, regex and unknown-property errors fail the row and the runner even if the underlying program exited zero. Keep platform-specific messages visible and justify any non-blocking classifications. Include gate assertions that a bad fixture returns nonzero when repairing a false-pass runner.
2. For a parse failure identify theme, resource URL, phase and source. Use Qt diagnostic location when present. When absent, isolate the offending complete rule or block with the same configured Qt parser in scratch, keeping braces and context intact. Compare against current and previous QSS and map the minimal failing input back to a property or selector and line/column. Check bundled QSS and any appended/generated fragments. Web pseudo-elements and `content` rules have caused unsupported-property warnings. Verify the current state assets before removing dead rules. Rerun the complete matrix after the final fix and report error counts for parse and unknown property explicitly.
3. Keep diagnostics and historical outputs in their own directories. Generate final screenshots, boards and JSON from the final build and current QRC/manifest in a fresh directory. Enumerate expected boards, screenshots and rows and compare with produced files. Decode every delivered image. For resource boards require a bijection between ledger rows/tiles and intended current effective QRC entries, with matching hashes and consumers. Reject retired SVGs, old pages, unresolved aliases, obsolete URLs and screenshots from previous runs. Include current run ID, inputs/build and output paths or hashes in the receipt.
4. Deliver raw logs and a structured row per mode × preset × requested scale × before/after when requested. Record actual style class and base/overlay count where applicable, Qt version/QPA, actual DPR and dimensions, registration and interaction assertions, settings or restart outcome, warning categories/counts, exit status and current screenshot links. Add protected paths and before/after hashes and full-application build outcome. Report resource closure, state/interaction and visual findings distinctly. A configured offscreen probe, full build, actual running application/plugin interaction, visual review and user approval each have their own result. Record Windows, macOS, Qt 6, fractional scaling and accessibility as measured or TODO individually. A Linux Qt 5 result covers its measured environment. Use the documented project agent toolchain for any automated full application operations.

## Framework selection and isolated Qt 5 diagnostics

1. Compare complete `QStyle`, theme/token/resource management, QSS templates and retaining the existing implementation. Cite the active build cache, project licence and versioned candidate CMake, licence and implementation. Record supported Qt versions/platforms, draw/geometry/hit-test/animation responsibilities, native/plugin integration, accessibility, maintenance and licence compatibility. Mark unknowns as TODO. If a fetch returns 404, locate the correct path in the pinned tree, as with Kvantum's nested build/README/style files. Qt Advanced Stylesheets is a theme/resource management candidate, while a QSS gallery is primarily sample styling. Verify each candidate's actual capabilities before recommending it.
2. When investigating upstream widgets, read the original implementation and exercise that original class beside the unmodified base widget on the same Qt and DPI. For ParaView inspect `pqComboBoxStyle` and `pqAdjustToCurrentComboBox` as present in the selected checkout. Compare closed geometry or pixel differences and popup behaviour/size at 1×/2×. Attribute differences to popup policy or current-item sizing when the source and probe agree. Verify the scope of a named colour palette from its consumers, including whether it affects rendering scenes rather than widget skins. Review full candidate styling on actual dense Qt 5 windows against Native/Fusion and the current backend with equal content/sizing. Compare the whole control, interaction and transitions, including keyboard and disabled states.
3. For a Qlementine v1.5.2 read-only Qt 5 diagnostic, pin and record the release source, for example `https://codeload.github.com/oclero/qlementine/tar.gz/refs/tags/v1.5.2`. Hash the archive, extract in an isolated workspace, record actual Qt version and snapshot the project and extracted upstream bytes. Set `upstream`, `work` and `qt_prefix` to the scratch extraction, scratch output and existing Qt 5 SDK. Test the unmodified upstream configure in a dedicated build directory and collect its full output and exit status.
   ```bash
   cmake -S "$upstream" -B "$work/build-upstream-qt5" -DCMAKE_PREFIX_PATH="$qt_prefix" -DCMAKE_DISABLE_FIND_PACKAGE_Qt6=TRUE > "$work/configure-upstream.log" 2>&1
   ```
4. If the entry point requires Qt 6, create a separate scratch CMake probe (`adapter`), deriving the complete library implementation list and relevant headers/definitions/generated headers from the pinned upstream CMake. Link existing Qt5 Core, Widgets and Svg and preserve applicable MOC/resources as needed. The recorded v1.5.2 probe used all 59 implementation entries. Verify the actual inventory. Leave upstream C++ untouched. Log the independent configure/build and any observed source failures. Example build commands with separate logs:
   ```bash
   cmake -S "$adapter" -B "$work/build-source-qt5" -DCMAKE_PREFIX_PATH="$qt_prefix" > "$work/configure-source-qt5.log" 2>&1
   cmake --build "$work/build-source-qt5" > "$work/build-source-qt5.log" 2>&1
   ```
   If a missing `QtTypeTraits` blocks further evidence, optionally add a scratch compatibility header implementing the required `qToUnderlying` using `std::underlying_type_t`. Expose it only to the diagnostic target. Reconfigure/rebuild and retain separate outputs for that pass. Record actual remaining API diagnostics and upstream source locations, such as `QPainterStateGuard`, `QVariant::typeId()` and `enterEvent(QEnterEvent*)`. Check extracted files byte-for-byte against archive members and recheck ACloudViewer's baseline. The requested read-only diagnostic uses the existing SDK and leaves dependencies and project sources untouched.
5. Publish a receipt with release URL/version/archive digest, project and upstream hash check, actual Qt/runtime platform, each command and exit code, source inventory, diagnostic-only alterations and error locations. Give separate verdicts for direct upstream support, code changes needed for backport and runtime acceptance. Stock v1.5.2 required Qt 6 and the Qt 5.15.2 source diagnostic hit API differences after bypassing configure. Failed diagnostic builds leave backport feasibility and runtime unverified. If auditing a later port, identify the exact patch and prove its actual build/runtime separately. For authorised integration follow the existing dependency contract and exercise the same production owner and dense window matrix.
