# Browser and full-tree acceptance of exact artifacts

Use only the verified run ZIP and version inputs described in [artifact and capacity evidence](<integration-maintenance.md#artifacts-and-capacity>). The script identifies its input by supplied SHA/run and resolved stage path; this label does **not** authenticate the artifact. Link verification metadata, replay log and clean staging/preservation receipt in each run's report. The script is a local probe, not deployment or a replacement for the existing fixture guards or interactive site checklist.

```bash
# SKILL_DIR is the resolved skill directory; SITE is the actual unified-deploy tree.
"$DOC_PY" "$SKILL_DIR/scripts/verify_merged_site.py" \
  --sha "$SHA" --run-id "$RUN_ID" --site "$SITE" --out "$EVIDENCE/real-before" \
  --versions "${EXPECTED_VERSIONS[@]}" --latest "$EXPECTED_LATEST" --plan "$PLAN"
```

Use versions in expected manifest order, from independently validated inputs. Use a fresh report dir outside the tree each time. Use the already verified Playwright interpreter/browser; if launch fails verify executable/install against the current guard environment, do not claim a test pass. Preserve first raw reports even if the harness is later corrected; execute a new run in another directory. Only serve trusted project build outputs on loopback, using a clean browser context without cookies; the script blocks external subrequests and reports them separately. For external URL/release checks use separate read-only evidence. The probe records the browser version and executable, ephemeral prefix, routes, width metrics and overflow elements, JS/HTTP errors, and decoded images for explicit checks. It emits JSON and Markdown with per-reference issues; nonzero means investigate, not automatically a site defect.

## Plan and coverage checklist

Provide a JSON plan with `pages` (array of entries below), and optionally `templates` (mapping of exact relative HTML paths to evidence strings). Paths/URL examples must be replaced with observed paths, not guessed. Each page accepts `path` (local path relative to mount), optional `final` (expected path/query/fragment, exact), `status` (initial HTTP status, default 200), `selector` (visible final DOM), `svg` (optional CSS selector for SVG links; target hrefs loaded locally must resolve), and `images` (list of expected actual image URLs, each relative to the final page or absolute local path). For each repaired reference, include its actual referring API page and image URL in the plan; scrolling/lazy loads must be exercised and decoded, not just requested directly. Record failures if expected DOM anchors are absent. Treat directory and explicit `index.html` equivalence only for root entries (the script compares root final URLs accordingly). Check exact final URLs for redirects and switches. Exercise the existing real-site checklist in [staging](<staging-and-browser.md#browser-on-the-actual-tree>) as well:

- Root, navigation/download controls, version manifest types/latest/order, sitemap, documentation redirect, each version root, C++ entry and common tutorial/Python API deep links. Select evidenced tutorial images; use actual notebook source links when CI doesn't ship notebooks. Use real SVG graph links, checking both `href` and XML XLink, and open at least one linked target from a real SVG page.
- Drive modern and legacy version controls dev↔stable on the common deep routes, record selected value, final browser URL and successful page. Separately exercise the expected missing-page fallback. Probe search by entering a known real symbol and verifying a result opens the expected page. These control interactions require the actual DOM/guard or Playwright calls (inspect live selectors before using, don't substitute simple GETs).
- Supply custom 404 cases with expected initial status 404 and final query/fragment for nested old flat URLs; include both dev and historical versioned misses with no redirect loops and no failed logo images. In Playwright use navigation/request observers from before `goto`; log network and JS errors, not just final successful DOM. Calibrate production against actual host responses, not the local server's assumptions.
- Widths 1280/1024/768/390/320 by default; use document/body scroll width plus element bounds and relevant styles. Distinguish a child intentionally scrolling inside a container from viewport overflow. The observed 1024px issue was nonwrapping gallery tabs; 390px was a flex child with long `pre` content. Fix layout at the owner (wrap and permit inner scrolling), not whole-page clipping. Compare new CSS versus original CSS in separate staging trees for a real positive and negative control.
- The static pass enumerates every published HTML/CSS/SVG file, including templates, and resolves declarative asset attributes, CSS `url`/`@import` and SVG references against served URLs, including percent-decoding and HTML base. Local resource findings record referring file/URL, raw value, resolved path and classification. It does not infer JS-computed URLs or parse arbitrary templating/complex escaped CSS; cover those with browser instrumentation and a scoped follow-up scan where present. Static SVG anchor checking and browser interactions complement each other. External references are not credited as local successes. Exempt a missing reference only by proving its file is an unused unrendered template (e.g. Doxygen analytics/header placeholder): verify the source/producer and no final rendered or reachable reference uses it, record proof per exact file. Never blanket-ignore Doxygen or historical prefixes. Keep all template rows in the report. Further classify actual defects (historical source, formula, third-party, plugin raw HTML) by their traced source rather than guessing from a name; preserve raw output and write attribution beside it.

## Production read-only

Read exact remote main with `git ls-remote origin refs/heads/main` (or the authorized remote), feature SHA/PR runs and main/release workflow metadata and logs. Look up Pages deployment/environment records read-only when available; correlate commit, run/attempt/job URL and deployment ID/timestamps, the publish step result **and** the later live verifier step result. Overall failure after a successful publish is possible. Record the actual site URL, HTTP results, manifest, headers/cache and retained content identity/asset hashes where applicable. Public content or a green job alone cannot prove which exact SHA is served: document the corroboration or explicitly mark unknown and distinguish previous deployment from new failed verification.

At the existing GitHub Pages production URL, use a real, fresh browser with network/console capture. Check homepage nav, download filters/controls and final asset targets, documentation entry, stable and dev deep links, search and result navigation, tutorial images (decode), real version switch destinations, legacy redirect with query/fragment, already-versioned 404 and local resources. Capture actual URL, result/status, selector/text/network evidence and time for each; do not count a fixture or local replay as production. No `push`, dispatch, deploy, upload or modification of release assets. Report candidate build, what is live, and production browser verdict as three independent conclusions.
